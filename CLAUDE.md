# Lion Safari Ticketing — working notes

Read [README.md](README.md) first. Requirements live in
`Lion_Safari_Ticketing_Production_Requirements.txt`; section numbers referenced in
code comments (spec §4.3, §7.2, …) point there.

## Rules that must not be relaxed

1. **Only a verified webhook or a staff cash confirmation may confirm a booking.**
   Browser input, payment redirects and scanner UI state prove nothing. The single
   path to `PAID` is `src/domain/payment/process.ts`.
2. **Every uniqueness rule stays a database constraint**, not just app logic. If you
   add a retryable operation, add the constraint that makes retrying safe.
3. **Money is integer paise.** Never floats, never rupees outside `src/lib/money.ts`.
4. **Amounts are recomputed server-side** in `src/domain/booking/pricing.ts` and
   re-checked against the provider payload before confirming.
5. **The webhook handler reads the raw request body.** Parsing and re-serializing
   JSON rewrites decimals and breaks the signature.
6. **Server time is authoritative.** Device clocks are stored for audit only.
7. **The scanner never receives raw ticket tokens or customer PII** — only token
   hashes (`src/domain/scanner/sync.ts`).
8. **State changes go through the transition functions** in `domain/booking/status.ts`
   and `domain/ticket/issue.ts`, which lock the row, validate the transition, and
   write both the audit log and the scanner change feed in the same transaction.
   There is no generic "set status" path.
9. **Users never see technical errors.** Throw `DomainError` with a `userMessage`;
   log the detail separately.

## After changing anything load-bearing

```bash
npm run typecheck && npm run build
npm run verify:all      # needs the dev server running
```

`verify:*` scripts in `scripts/` are the regression net for the failure scenarios
in spec §14. When you add a guarantee, add a check there.

## Local setup gotchas

- Two processes are needed: `npm run dev` and `npm run worker`.
- Route types (`PageProps`, `LayoutProps`) are generated by `next build`/`next dev`.
  A fresh clone typechecks only after one build.
- `.env.local` is gitignored; `.env.example` is the template and is committed.
